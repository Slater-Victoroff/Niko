# Experiment log: Niko (latent dynamics surrogate for The Well's physics datasets)

A running record of architecture search, training methodology, and dataset generalization — condensed to conclusions and numbers, not the full blow-by-blow. Full history is in git if needed. This file didn't exist before this session; the "pre-session" note in §1 covers what's recoverable about earlier work from git archaeology.

**Task** predict future frames of a 2D physical simulation from a short context window, via encode → latent-space operator rollout → decode &nbsp;·&nbsp; **Datasets** The Well (rayleigh_benard, active_matter, shear_flow) &nbsp;·&nbsp; **Compute** Docker + 2x RTX 5000 Ada

---

## Where things stand

> **The `split_encoder`/`complex_operator` architecture (the one actively developed this session) had never been trained on a full dataset before now — a clean retrain beat the plain baseline meaningfully.** See §2-3: an FFT-fed complex branch (real spectrum instead of a from-scratch learned CNN) matches baseline quality at half the encoder params, and once its wide-variant's divergence bug was root-caused and fixed (zero-init + a bounded per-step multiplicative ceiling), it *slightly* beat baseline on a broad8 subset (0.211 vs 0.216 valid_loss, 7 epochs).
>
> **Fully conditioning the operator's diffusion/skew terms on Rayleigh/Prandtl (previously silently global) gave a small, real, seed-consistent improvement (§3).**
>
> **A pure-reconstruction autoencoder pretrained on the same encoder/decoder architecture landed meaningfully below every joint-trained full model (§4) — confirms the encoder/decoder round-trip, not the operator, is the binding ceiling on how low any of these numbers can go.** The operator's own marginal contribution to end-to-end error is already small; further gains need encoder/decoder capacity, not operator tuning.
>
> **A from-scratch JEPA-style operator (frozen pretrained encoder/decoder, pure latent-space MSE loss, no decoder in the training loop) plateaued badly — a settled negative result, not a training-time artifact (§5).** Decoded vrmse got stuck at ~11.3-11.5 for 4 straight epochs after an initial drop from ~12.1, dramatically worse than any joint-trained model (~0.2-0.6 range across all three datasets). Killed before completion.
>
> **Generalized the whole pipeline beyond rayleigh_benard to any Well-format dataset (§6) — two real, non-obvious bugs found and fixed along the way, not just plumbing.** `active_matter`'s square 256x256 grid broke the existing length-based axis inference (ambiguous when x_len==y_len); switched to a position-based convention, verified against all three datasets' actual on-disk layout. Filename-regex param parsing was replaced with reading `simulation_parameters` directly from each file's own HDF5 attrs (dataset-agnostic, no per-dataset regex) — but the exact-float-equality matching this enabled silently dropped `--param-subset` combos whose value isn't exactly binary-representable (0.1, 0.2, ...), a real regression caught empirically (2 of 8 shear_flow combos silently missing) and fixed with a significant-figure-rounded match key.
>
> **First real training runs on both new datasets are done**: `active_matter` (tensor-field decoder heads, concentration+velocity+D+E) reached valid_loss 0.446-0.567 over 4 epochs before being stopped; `shear_flow` (streamfunction-derived velocity, physically justified there unlike active_matter, corrected 8-combo subset) ran the full 7 epochs, best valid_loss 0.385 (epoch 2, essentially tied with epoch 6's 0.388) but ended on a clearly overfit final epoch (train 0.248, valid 0.668) — use the epoch 2 or 6 checkpoint, not the last one. Neither number is comparable to rayleigh_benard's or to each other's — different physical systems, different channel compositions, `well_style_vrmse`'s per-channel variance normalization operates on a different distribution each time.
>
> **§8 supersedes §2-3's encoder direction: the entire complex/tucker/spectral encoder family (`split_encoder.py`, `ComplexTransportOperator`, tucker branch/operator) has been deleted from the codebase.** Under this session's genuinely-controlled apples-to-apples protocol (a plain real-only baseline had never actually been run before — it turns out to matter), none of it beat a `SequenceConvEncoder` + real `FiLMHelmholtzTransportOperator` baseline, and the complex branch was consistently harder to train (slower convergence, occasional divergence) for no measured benefit. §2-3's numbers below are left as an accurate historical record — they were real, measured results at the time — but the code they describe no longer exists; see §8 for why and what replaced it. **Where things actually landed: `context_cond_pooled_helmholtz` — the plain real baseline, conditioned not by ground-truth Rayleigh/Prandtl but by a pooled per-frame-trunk encoder inferring conditioning straight from context — hit valid_loss 0.229, tying the ground-truth-param version exactly, with none of the complex-branch instability.**

## 1. Pre-session context, package restructure, and a GPU driver incident

**Pre-session (recovered from git archaeology, not directly observed):** an earlier architecture search (flat `src/*.py` layout, committed May 23) settled on a `sequence_conv` encoder + `film_helmholtz` operator recipe, ctx6/roll6, converging to ~0.225-0.28 val_loss on the full rayleigh_benard dataset (35 combos) after dozens of runs. A follow-up physics-informed `DirectFieldOperator` baseline (pressure derived analytically from buoyancy via a hydrostatic Poisson relation, streamfunction-derived divergence-free velocity) was started but never got past 4 epochs (ctx1/roll1, VRMSE ~0.72-0.74, unconverged) before the session ended.

**This session opened on an uncommitted package restructure** (flat `src/` → installable `src/niko/` package, new `eval/`/`export/` subpackages) sitting alongside a broken GPU: `unattended-upgrades` had silently bumped `nvidia-driver-580` mid-session (580.159.03 kernel module vs 580.173.02 userspace), and Xorg holding the module open meant only a reboot fixed it. Committed the restructure to a new branch (`explore/fft-complex-encoder`) after the reboot, keeping checkpoints untracked (git-ignored) and out of the diff.

**`--param-subset` (a JSON list of specific parameter combos) added to `train.py`/`dataloader.py`** for fast iteration without paying for the full dataset — this is what every "broad8" run below uses (8 combos spanning the parameter range, vs. all 35 for rayleigh_benard).

## 2. FFT-fed complex-branch encoder: does a real spectrum beat a learned one?

**Motivating question**: `split_encoder`'s complex branch (`complex_net`) is a from-scratch learned CNN trying to invent a complex latent from raw pixels. Does feeding it an *actual* `rfft2` of the last frame instead work as well, more cheaply?

**`split_encoder_fft`**: complex branch replaced by `rfft2_crop` (orthonormal, exact spectral downsampling — no learned approximation) + a single 1x1 conv projection. Half the encoder params (80,764 vs 163,128), ~half the forward time, no quality loss on an initial 2-combo/3-epoch check (0.645 both variants).

**First attempt at scaling the complex branch back up diverged.** `split_encoder_fft_wide` (wider depthwise kernel in `real_net`/`fuse_net`'s `ConvNeXtBlock`s, `complex_proj` untied into per-frequency-bin weights via a new `LocallyConnected1x1` — same FLOPs as the shared conv it replaces, ~8,300x more params in that one projection) trained cleanly through epoch 3, then diverged progressively worse through epoch 7 (one isolated spike at epoch 4, never recovered, final valid_loss 1.66 vs epoch-3's 0.216). Root-caused: `complex_proj`'s output layer wasn't zero-inited (unlike every other newly-conditioned term in this codebase), so an uncontrolled random-scale signal fed the operator's multiplicative `spectral_grid * exp(amplitude + i*rotation)` term every rollout step — compounding over 6 steps. **Fixed with two changes**: zero-init `complex_proj`'s output layer (matches this codebase's established convention), and a new `amplitude_scale` parameter on `TransportOperator` (default 1.0, unchanged behavior) tightening the per-step ceiling from `exp(±1)≈2.72x` to `exp(±0.5)≈1.65x` for the wide variant specifically. **Retry (broad8, 5 epochs) held clean through the exact epoch-4 point that broke before** — best result 0.261 at epoch 4, smooth monotonic improvement, no spikes.

**`fused_spectral_encoder`**: goes further — `irfft2`s the complex branch back to real space and fuses with `real_net`'s output via a learned conv into a single real latent, no persistent `spectral_grid` at all (pairs with `film_helmholtz`, not `complex_operator`, since there's nothing left for a complex rotation term to act on). Full-dataset (35 combos) comparison against baseline, 3 epochs each: essentially tied on final quality (0.266 baseline vs 0.263 fused) but fused reached that quality in a third of the epochs (already at 0.263 after epoch 1).

**`fused_spectral_encoder_big`**: same fused design, sized up via two compute-cheap levers — wider depthwise kernel (7→11, cheap since depthwise scales with channels not channels²) and the same `LocallyConnected1x1` trick for `complex_proj` (113K → 2.5M encoder params, ~22x). Confirmed same throughput as the small version (~430ms/batch). Hit one real bug: SOAP's preconditioner tried to eigendecompose an 8256x8256 covariance matrix for the new wide-axis weight and crashed cusolver — fixed with a `--soap-max-precond-dim` flag (default unchanged at 10000, explicitly capped to 1024 for this architecture). Broad8/7-epoch result: 0.211 best (epoch 7), a small real improvement over the small fused encoder's own 0.216 best, but the extra ~22x params bought only a marginal gain — consistent with §4's finding that encoder capacity isn't the dominant bottleneck.

## 3. Fully conditioning the operator

**Found**: of `film_helmholtz`'s four real terms (advection/diffusion/forcing/skew), only advection and forcing were actually FiLM-conditioned on Rayleigh/Prandtl — diffusion (`log_nu`) and skew (`skew_raw`) were single global learned parameters shared across every physical regime, despite `broad8` spanning 4 orders of magnitude in Rayleigh.

**Fixed**: `DiffusionTerm`/`SkewTerm` now predict their (`log_nu`/skew-generating matrix) per-sample from `cond` via a small `Linear` head, zero-inited so both start identical to the old unconditioned behavior. Confirmed via direct gradient checks that both terms' own weights get real gradient immediately, while gradient reaching further back into `param_encoder` itself is provably exactly zero for the first ~2 optimizer steps (every conditioning gate in this codebase is zero-inited, and `d(Wx+b)/dx = W = 0` blocks the chain until the gate itself moves) — verified empirically (0.0 → 0.0 → 0.0037 → 0.039 over 4 real steps), not just asserted.

**Broad8/7-epoch result (`fused_cond_broad8`, small fused encoder)**: 0.220 best (epoch 5-6), edges out the unconditioned version's 0.216 — real but modest.

## 4. Autoencoder pretraining: where's the actual ceiling?

**Built `train_autoencoder_baseline.py`**: `param_encoder`+`encoder`+`decoder` only, no operator, trained to reconstruct the last context frame directly (no rollout, no forward-prediction task). Measures the encoder/decoder round-trip's information ceiling, independent of the harder forward-time-prediction job.

**Baseline architecture (`split_encoder`+`shared_heads`), broad8, 7 epochs: bottomed at 0.135 (epoch 5), below every joint-trained full model's own best (0.211-0.280 across all variants in §2-3).** Since a *perfect* operator, holding encoder/decoder fixed, can only ever asymptotically approach the reconstruction floor (decoding the exactly-correct predicted latent is exactly the autoencoding task), this means the operator has already extracted most of the value available from this encoder/decoder — further operator-only tuning has limited headroom; the real lever for pushing error down further is encoder/decoder capacity itself.

## 5. JEPA-style operator training: a settled negative result

**Built `train_jepa_operator.py`**: reuses the frozen (`param_encoder`, `encoder`, `decoder`) from §4's autoencoder checkpoint, trains *only* a new operator via a pure latent-space MSE loss (`LatentState.grid` of predicted vs. target latent) — no decoder in the training loop at all. No stop-gradient/EMA target network needed (unlike from-scratch two-tower JEPA): the encoder is frozen and was pretrained via reconstruction, which already structurally rules out representation collapse.

**Target-latent construction**: since the frozen encoder needs a full 6-frame context window (not a single frame) to encode anything, the target for future step `t+k` is a proper re-encoded 6-frame window ending at `t+k` — turns out context (`t-5..t`) + rollout targets (`t+1..t+6`) from a standard batch already span exactly the 12 consecutive frames needed for all 6 sliding windows, no dataloader change required.

**Result (broad8, `complex_operator`, killed at epoch 6/7): plateaued hard.** Decoded vrmse (computed only for comparison, not part of the training loss) went 12.14 → 11.43 → 11.48 → 11.27 → 11.41 across epochs 1-5 — real early progress, then stuck, 4 straight epochs with no further improvement. Compare to any joint-trained model's 0.2-0.6 range: roughly 20-50x worse. Killed before completion — this reads as a settled negative result for "pure latent-space loss, frozen pretrained encoder/decoder, complex_operator" specifically, not proof against JEPA-style training in general (a fine-tuned or differently-regularized encoder, a different loss form, or a different operator architecture might behave completely differently — untried).

## 6. Generalizing beyond rayleigh_benard: active_matter and shear_flow

**Motivation**: two more Well datasets, `active_matter` and `shear_flow`, were already downloaded locally but ~40% of both was corrupted (truncated incomplete downloads, confirmed via direct HDF5-open checks — 32/82 and 37/84 files respectively). Root cause: `the-well-download`'s underlying `curl --continue-at -` resume mechanism, interrupted mid-batch at some earlier point and never rerun to completion. Simply re-running the same download command (`the-well-download --dataset <name> --base-path /home/sl8rv`) resumed/completed every file correctly — both datasets are now 100% valid (82/82, 84/84).

**Real structural differences from rayleigh_benard, confirmed by direct HDF5 inspection, not assumed from filenames:**
- `shear_flow`: pressure + tracer (2 scalars) + velocity (vector) = 4 channels, same shape family as rayleigh_benard (just tracer instead of buoyancy) — close to a drop-in fit. Grid 256x512 (double RB's Y-resolution).
- `active_matter`: concentration (1 scalar) + velocity (vector) + **D, E (two rank-2 tensor fields, 2x2 each)** = 11 raw channels, no pressure field at all. Grid 256x256 (**square** — a real problem, see below). 3 params (L constant, zeta, alpha — alpha negative).

**Generalized the dataloader (`field_spec` mechanism)**: replaced hardcoded pressure/buoyancy/velocity HDF5 keys with an ordered list of `{key, n_components}` specs (1=scalar, 2=vector, 4=flattened 2x2 tensor, row-major). One unified `_field_to_t_c_yx` helper subsumes the old separate scalar/vector-only logic and extends naturally to tensor fields. **Regression-tested bit-for-bit against the old rayleigh_benard code path** before trusting the generalization on new data.

**Bug found and fixed: axis inference was length-based, ambiguous on `active_matter`'s square grid.** The old `_infer_xy_axes_from_shape` matched axes by comparing their length to `dimensions/x`/`dimensions/y` — works when x_len≠y_len (rayleigh_benard, shear_flow) but is fundamentally ambiguous when they're equal (`active_matter`'s 256x256). Switched to a position-based convention (x,y always axes 1,2, confirmed true across all three datasets' actual on-disk shape), with length used only as a sanity check where unambiguous.

**Bug found and fixed: param reading switched from filename regex to reading `simulation_parameters` out of each file's own HDF5 attrs** — dataset-agnostic (works identically for rayleigh_benard's 2 params, shear_flow's 2, active_matter's 3), no per-dataset regex. This is strictly more general, but introduced a real regression: comparing the resulting float32-precision values against human-written JSON combos via exact tuple equality silently dropped any combo with a decimal that isn't exactly binary-representable (`float32(0.1)` upcast to float64 ≠ Python's `0.1` literal) — caught empirically when a `shear_flow` `--param-subset` request for 8 combos silently returned only 6. **Fixed** with a significant-figure-rounded match key (`_params_match_key`, 6 sig figs) used only for matching; the actual conditioning values fed to the model stay at full stored precision. Confirmed fixed: same 8-combo request now matches all 8.

**Decoder generalized**: `scalar_field_names` (replaces the fixed pressure+buoyancy pair when set — e.g. `["concentration"]` for active_matter, `["pressure", "tracer"]` for shear_flow) and `tensor_field_names` (one `Conv2d(hidden_dim, 4, kernel=1)` head per tensor field, same pattern as every other head, kept as 4 flat channels not reshaped to `(...,2,2)`). Both default to `None`/empty — every existing config/checkpoint unaffected. `zero_mean_pressure` only applies when `"pressure"` is literally in `scalar_field_names`, not assumed for an arbitrary scalar. Confirmed via direct forward+backward checks (not just shape checks) that: gradients reach every new head, `zero_mean_pressure` correctly zeros only the pressure channel's spatial mean (~1e-9) while leaving other scalars unconstrained, and the streamfunction-derived-velocity path works correctly when combined with the new generalized `scalar_field_names` branch (previously only exercised via the old fixed-FieldState path).

**Param encoder generalized**: new `MultiParamEncoder`, N params each with an independently configurable transform (avoids `log10`-on-negative-`alpha` producing NaN — `active_matter` uses `identity` for all 3 params given the observed ranges; `shear_flow` uses `log10`/`log10` for Reynolds/Schmidt, both wide-multiplicative-range).

**`use_streamfunction` chosen per-dataset on physical grounds, not by default**: on for `shear_flow` (classic incompressible viscous flow + passive scalar transport — Reynolds/Schmidt numbers are specifically incompressible-flow parameters, the divergence-free assumption is well-justified) and explicitly off for `active_matter` (an active-nematic/polar-fluid constitutive model where incompressibility isn't a given, avoided rather than assumed).

**First real training runs:**
- `active_matter_full` (all 45 train / 16 valid files, ctx6/roll6, `sequence_conv`+`film_helmholtz`+concentration/D/E heads): 0.567 → 0.449 → 0.470 → 0.458 over 4 epochs (stopped mid-epoch-5). Notably fast per-epoch (~15-20min) given the much smaller total dataset (44GB) than rayleigh_benard.
- `shear_flow_broad8` (8-combo subset, same recipe as the rayleigh_benard broad8 runs, `use_streamfunction=True`): hit a real CUDA OOM at `batch=8` (30GB+, crashed) — shear_flow's 256x512 grid is double rayleigh_benard's Y-resolution at the same batch size, and early un-downsampled layers scale activation memory roughly with pixel count. Fixed by dropping to `batch=4`; ran cleanly (~21GB) through all 7 epochs. Valid loss by epoch: 2→0.385, 3→0.473, 4→0.633, 5→0.412, 6→0.388, 7→0.668, while train fell monotonically the whole way (0.279→0.248). Best checkpoints are epoch 2 (`model_ep2_ctx6_roll6_vloss0.3854_lr1e-03_b4.pt`) and epoch 6 (`model_ep6_ctx6_roll6_vloss0.3881_lr1e-03_b4.pt`); the final epoch is the worst of the run and shouldn't be used as "the" checkpoint.

## 7. Tucker/complex/spectral conditioning: an extended dead end, and what survived it

This section covers a long thread of architecture exploration on rayleigh_benard/broad8 (ctx6/roll6, 7-epoch protocol throughout unless noted) that ultimately concluded the entire complex/tucker/spectral encoder direction (§2-3, and everything below) wasn't earning its keep — the code for all of it has since been deleted (see end of this section). Kept for the record because the negative results and the bugs caught along the way are genuinely informative, and because two things *did* survive: the context-inferred-conditioning idea, and a standalone param-inference regressor.

**Tucker encoder/operator.** Built a real (non-complex) rank-limited Tucker-2 branch — one factor from a vertical collapse, one from a horizontal collapse, a dense core from a small conv net — both fused into the main latent (`FusedTuckerSpectralEncoder`) and kept separate for an operator to evolve (`SplitTuckerEncoder` + `TuckerHelmholtzTransportOperator`, reusing the exact 2D Helmholtz terms on the core, new 1D analogs for the factors). **Caught a real design bug before it shipped**: `evaluate_tucker` is trilinear in `(core, U_h, U_w)`, so zero-initing `core` (the standard convention for a new additive term) doesn't fade the branch in — it makes the loss exactly independent of `U_h`/`U_w` too (`dZ/dU_h = core⊗U_w = 0` when `core=0`), silently blocking their own operator terms from ever training. Fixed with a `zero_init_core` flag (off when the operator keeps the core live). **Result: no measurable difference from baseline** once trained end-to-end — killed mid-run once the operator variant's gradient checks passed but the loss curve didn't distinguish itself from the control.

**The plain real-only control had never actually been run before.** `plain_helmholtz`: `SequenceConvEncoder` (real grid only, no complex/tucker branch at all) → `FiLMHelmholtzTransportOperator` → `SharedTrunkFieldHeadsDecoder`, ground-truth `param_encoder`. Broad8/7-epoch: **valid_loss 0.229 (best)** — competitive with or better than every branched-encoder variant in §2-3, run under the exact same protocol for the first time. This reframed the rest of the session: is the complex/tucker branch complexity buying anything at all?

**Param inference: predicting Rayleigh/Prandtl directly from context, decoupled from the main model.** `ContextParamRegressor` (context stacked as channels, fixed ctx6) and `PooledSequenceParamRegressor` (shared per-frame trunk + spatial pool + temporal mean pool, works at any sequence length) — trained via plain supervised regression against the dataset's own ground-truth params, in each param's own transform space (`log10` for both Rayleigh/Prandtl, since raw-space MSE is dominated by Rayleigh's 4-orders-of-magnitude range). **`ContextParamRegressor` (stacked, ctx6) reached transform-space MSE 0.0435** — this became the reference number for everything downstream. A static post-hoc pooling test (grouping an already-trained checkpoint's per-window predictions by ground-truth combo, averaging in transform space) showed pooling reduces relative error but doesn't reveal much beyond what training-time pooling already gets — noise averages out, but the single-window number was already fairly good.

**Context-inferred conditioning: skip the params entirely.** Instead of inferring `(Rayleigh, Prandtl)` explicitly and feeding *that* into the existing `param_encoder` path (a 2-number bottleneck), built `ContextCondEncoder`/`PooledContextCondEncoder` as drop-in replacements for `param_encoder` itself — same `[B, cond_dim]` output contract consumed by the same FiLM layers, but trained fully jointly via the normal rollout/reconstruction loss, no explicit params target, no bottleneck forcing the internal representation to literally equal the two physical numbers. **`PooledContextCondEncoder` (per-frame shared trunk, same pooling architecture as `PooledSequenceParamRegressor`) reached valid_loss 0.229 — tying the ground-truth-param baseline exactly, while never using a single ground-truth physical parameter anywhere in training.** The stacked variant (`ContextCondEncoder`) reached only 0.237 — the per-frame-trunk-then-pool inductive bias (shared weights across context frames, no frame-position-specific filters) mattered more than raw parameter count.

**Interpretability probe: does the learned cond embedding actually encode the physical params?** Froze the trained `context_cond_pooled_helmholtz` checkpoint, trained a small 2-layer MLP on top of its 32-dim cond embedding to regress back to `(log10 Rayleigh, log10 Prandtl)`. **Plateaued at transform-space MSE 0.096 — about 2.2x worse than the dedicated `ContextParamRegressor`'s 0.0435** — the embedding is useful for prediction (ties the ground-truth baseline on the actual task) but isn't a clean, linearly-recoverable encoding of the literal two numbers; it's evidently encoding *something else* that correlates with but isn't isomorphic to `(Rayleigh, Prandtl)`. Also tested a "rounding rule" (snap each prediction to its nearest neighbor among the 8 known `broad8` combos, since ground truth is always exactly one of them): **rounding never helped, across all 8 probe-training epochs**, even as exact-match rate climbed to 88.6% — the ~11-17% of wrong snaps jump a full discrete grid step and cost more in squared error than the correct snaps save. Continuous output beat discretized output throughout.

**Resurrected the complex/fft branch once more, now paired with context-inferred conditioning — still didn't work.** `context_cond_pooled_fft` (`split_encoder_fft` + `complex_operator`, cond from `PooledContextCondEncoder`): valid_loss 0.330 best (final epoch, after a mid-run dip to 0.634) — clearly behind the real-only 0.229. Hypothesis: the complex terms' FiLM cond came from spatial pooling with no explicit access to frequency content, a bad match for a phase-rotation term. Built `SpectralContextCondEncoder` (same pooling architecture, but the trunk runs on an `rfft2` of the context instead of raw pixels) feeding *only* `ComplexAmplitudeTerm`/`ComplexRotationTerm` in parallel with the existing spatial cond. **This helped**: 0.304 best, smoother monotonic convergence than the spatial-only version — confirmed the hypothesis. Along the way, found and verified (not just asserted) that `ComplexAmplitudeTerm`/`ComplexRotationTerm` are *doubly* zero-inited (both the internal FiLM layer and the output conv), unlike every other conditioned term's single gate — this delays gradient reaching a dedicated cond source by 2 optimizer steps instead of 1, a real but subtle difference from the codebase's established convention. **Two follow-ups still didn't close the gap to real-only**: switching the complex terms to normal (non-zero) init, to remove the 2-step gradient delay, made the early epochs *worse* (uncontrolled perturbation from step one) without a compensating late-training win over 4 epochs of observation; a `CoConditionMixer` (concatenate spatial+spectral cond, project back out to two new cond vectors, normal init, direct replacement not a residual) plateaued around 0.60-0.61 for 4 straight epochs — genuinely stuck, not just slow. Both runs were stopped early once the pattern was clear.

**Conclusion and cleanup**: after this whole extended thread, nothing beat or meaningfully complemented the plain real-only `context_cond_pooled_helmholtz` result (0.229). Deleted the entire complex/tucker/spectral encoder family: `encoders/split_encoder.py` (`SplitEncoder`, `FusedSpectralEncoder`, `FusedSpectralEncoderBig`, `FFTSplitEncoder`, `FFTSplitEncoderWide`, `FusedTuckerSpectralEncoder`, `SplitTuckerEncoder`, `rfft2_crop`), `encoders/tucker.py`, `operators/tucker_terms.py`, `ComplexTransportOperator`/`ComplexRotationTerm`/`ComplexAmplitudeTerm`/`TuckerHelmholtzTransportOperator`, `SpectralContextCondEncoder`/`CoConditionMixer`, and `LatentState`'s `spectral_grid`/`real_tucker`/`complex_tucker`/`channel_sgrid`/`phys_sgrid` fields — `LatentState` is back down to just `real_grid`/`aux`/`meta`. Also reverted the FiLM double-zero-init change (`ComplexAmplitudeTerm`/`ComplexRotationTerm` no longer exist to need it). **Kept**: the plain real operator family (§3's full-conditioning fix still applies), `ContextCondEncoder`/`PooledContextCondEncoder` (the actual winning direction), and the standalone param-inference regressors + interpretability probe (genuinely useful, orthogonal findings, not part of the abandoned branch). All corresponding configs (`streamheads*.yaml`, `context_cond_pooled_fft*.yaml`) and their checkpoint directories were removed too; `plain_helmholtz.yaml`/`context_cond_helmholtz.yaml`/`context_cond_pooled_helmholtz.yaml` remain as the current reference configs.

## 8. Open threads

- `shear_flow_broad8`'s valid loss got visibly noisier/worse in its back half (epoch 4: 0.633, epoch 7: 0.668) while train kept improving monotonically — not investigated further (batch=4 is smaller than every other broad8 run here, which may just mean noisier gradient estimates; could also be an early sign this recipe overfits shear_flow's smaller effective dataset). Worth a longer run or a dropout/weight-decay pass to see if it's a real ceiling or just this particular run.
- `active_matter_full`/`shear_flow_broad8` numbers aren't comparable to rayleigh_benard's or to each other — different physical systems, different channel compositions, no shared baseline to compare against yet. Worth an autoencoder-pretraining pass (§4's method) on each to get their own reconstruction-floor reference points, once there's time.
- §5's JEPA result is only a negative result for one specific setup (frozen encoder, `complex_operator`, pure latent MSE) — fine-tuning the encoder under the JEPA loss (with a stop-gradient/EMA target to prevent collapse) or a different loss form were both explicitly deferred, not tried.
- §2's `fused_spectral_encoder_big`'s ~22x param increase bought only a marginal quality improvement (0.216→0.211) — consistent with §4's ceiling finding, but the decoder and operator have the same cheap-scaling levers (wider depthwise kernel, locally-connected untying) available and completely untried.
- None of §2-5's architecture variants (FFT-fed encoders, full conditioning, autoencoder pretraining, JEPA) have been tried on `active_matter`/`shear_flow` yet — everything there so far is the simplest possible baseline choice at every layer, deliberately, as a first correctness/wiring test rather than an architecture decision.
- `active_matter`'s tensor fields (D, E) have no dedicated loss weighting or physics-consistency diagnostic yet — `well_style_vrmse`'s generic per-channel variance normalization treats all 11 channels uniformly, untested whether that's actually reasonable for a rank-2 tensor field's own variance structure.
- The legacy `sequence_conv`+`film_helmholtz` checkpoints from before this session (§1, ~0.225 best) were never reconciled with any of this session's numbers — different encoder entirely, no direct comparison attempted.
- §7's `PooledContextCondEncoder` result (0.229, tying ground-truth params) was only run on rayleigh_benard/broad8 — untried on `active_matter`/`shear_flow`, where a context-inferred conditioning signal might matter even more (more params to infer for active_matter's 3, or could fail differently given shear_flow's smaller effective dataset per §7 above).

## 9. Conserved-subspace latent operator ("conserved head") — mechanism smoke test

**Motivation**: `HelmholtzTransportOperator`'s name is a misnomer worth flagging — `SkewTerm` is a per-sample skew-symmetric channel-mixing matrix applied as a forward-Euler step (`z + K·z`), not a literal Helmholtz (divergence-free/curl-free) decomposition, and it's only *infinitesimally* norm-preserving: nothing stops its accumulated per-step error from drifting over a multi-step rollout. There was no mechanism anywhere in the latent space with an actual architectural conservation guarantee — the only exact structural constraint in the whole model is decoder-side and physical, not latent (`use_streamfunction` decodes velocity as `curl(ψ)`, divergence-free by construction, chosen per-dataset).

**Design**: reserve `conserved_channels` of `latent_dim` as a dedicated subspace. A new `ConservedRotationTerm` (`operators/transport_terms.py`) predicts a per-sample skew-symmetric generator `K(cond)` on just that subspace and applies the true matrix exponential `R = expm(K)` — an exact orthogonal map, not an Euler approximation — so the per-pixel L2 norm (and therefore total spatial energy) of that subspace is invariant to floating-point precision, every step, regardless of training. `TransportOperator.forward` masks every other term's (advection/diffusion/forcing/skew/local_attention) output to zero on that channel slice before summing, so only `ConservedRotationTerm` may ever write it — other terms can still *read* it (full `z.real_grid` is passed in). New presets `ConservedHelmholtzTransportOperator`/`FiLMConservedHelmholtzTransportOperator` (advection+diffusion+skew+forcing, same as `HelmholtzTransportOperator`, plus the reserved subspace); `conserved_channels=0` is the default and reproduces the exact prior behavior (confirmed bit-identical, not just close). Config: `context_cond_conserved_helmholtz.yaml` (`conserved_channels=4` of `latent_dim=16`, a first guess, untuned).

**Mechanism checks (synthetic tensors, `test_conserved_operator.py`)**: `conserved_channels=0` bit-identical to `HelmholtzTransportOperator`; `ConservedRotationTerm` is an exact no-op at init (zero-inited generator → `K=0` → `R=I`); after perturbing all parameters and rolling out 25 steps, conserved-subspace per-pixel L2 norm drift is ~1e-5 relative (fp32 `matrix_exp` precision floor, not architecture leakage) while the free channels change substantially (mechanism isn't accidentally freezing the whole latent) and gradients reach both the conserved generator and the free-channel terms.

**Integration + real-data check**: ran `train.py` with `context_cond_conserved_helmholtz.yaml` on real `rayleigh_benard` data (ctx4/roll4, 1 train file, 5 steps) — built, trained, and ran the full physics-diagnostics suite with no shape/wiring errors, loss fell over the 5 steps (1.63 → 1.31). Then reloaded that checkpoint and rolled out 12 steps on a real validation batch (`test_conserved_real_data.py`): conserved-subspace norm drift stayed ~4e-6 relative on trained weights + real data, while the free channels moved by a real amount (mean abs change 0.43) — the invariant holds outside the synthetic-tensor setting it was designed against.

**Not yet done at smoke-test time**: no real training-to-convergence run, no comparison against plain `HelmholtzTransportOperator`/`FiLMHelmholtzTransportOperator` on a shared protocol, `conserved_channels=4` unswept, and the *literal* Helmholtz (div-free/curl-free spectral) decomposition variant discussed alongside this one — projecting a chosen 2-channel latent slice via `k̂(k̂·V)` in `spectral_grid` — is a different, untried design, not what got built here.

**First real ablation (quick2/7-epoch, `film_helmholtz` vs `film_conserved_helmholtz` conserved_channels=4, ctx6/roll6/batch8, single seed each, same code state, launched back-to-back on the two GPUs)**: speed/param overhead from the mechanism itself is negligible — 422.8ms vs 427.1ms/batch steady-state (~1%, consistent with a `matrix_exp` on a batched 4x4 matrix costing nothing next to the conv stack), +528 params (0.1% of the 465k-param model, exactly `cond_dim(32)*conserved_channels^2(16)+16` from `generator_head`). **But the accuracy cost is real**: valid_loss led narrowly for the conserved variant at epoch 3 (0.2656 vs 0.2733) but baseline pulled ahead from epoch 4 on and stayed ahead through epoch 7 (**baseline 0.2389 vs conserved 0.2542, ~6.4% worse**), every one of the last 4 epochs. Reserving 4/16 channels as a single dense, write-locked rotation block costs real free-channel capacity on this protocol — more than the early epochs suggested. Single seed, quick2 (not the broad8 protocol behind this file's other reference numbers) — a real signal, not a settled result.

**Follow-up: block-diagonal `ConservedRotationTerm`.** The single dense `n_conserved x n_conserved` block forces every conserved channel to share one generator (one invariant for the whole reserved subspace). Generalized `ConservedRotationTerm` to take `n_blocks` (default 1, exactly the original behavior — regression-tested bit-identical): splits the conserved subspace into `n_blocks` independent `block_size = n_conserved/n_blocks` chunks, each its own conditioned generator/exact rotation, no cross-block mixing — each block is now a *separate* conserved quantity instead of the whole subspace sharing one. `TransportOperator`/`ConservedHelmholtzTransportOperator`/`FiLMConservedHelmholtzTransportOperator` all take a new `conserved_blocks` kwarg (default 1, flows straight through YAML configs, no `build.py` changes needed). Confirmed per-block energy conservation holds independently (no cross-block leakage) both on synthetic tensors and on a real trained checkpoint rolled out on real data (~3e-6 relative drift per block, 12 steps).

**Alternative direction: a physically-structured complex/phase branch, as a replacement for the ad hoc one rather than an addition to the plain real operator.** The existing complex branch (§2-3/§7's `complex_term`, resurrected for `FoundationModel`) rotates an *arbitrary* learned complex latent (`complex_proj`'s output) with no physical meaning -- consistent with its own modest, not-dramatic gains (0.211 vs 0.216 on the older broad8/7-epoch protocol, not this session's numbers). Hypothesis: a phase rotation is physically the *right* operation for a divergence-free (solenoidal) vector field specifically (Kelvin's-circulation-theorem territory), so giving `ComplexRotationTerm`'s mechanism something physically real to act on, instead of an arbitrary channel set, might do better than either the arbitrary complex branch or this session's raw-channel conserved subspace.

Built as two new `TransportOperator` terms (`operators/transport_terms.py`), both operating directly on a designated 2-channel `real_grid` vector-pair, recomputed fresh from the *current* state every rollout step (not initialized once like `FoundationModel`'s `complex_proj`) -- deliberately NOT using the reserve-and-mask pattern from `ConservedRotationTerm`: masking would freeze the irrotational part, which should stay free (compressive/pressure structure isn't static), so every other term (advection/diffusion/forcing/skew) still fully acts on the same 2 channels, same as any others. Both fit the existing additive-terms-sum contract as-is -- zero changes to `TransportOperator.forward` or `LatentDynamicsModel`, just two new `REAL_TERM_BUILDERS` entries:
- `HelmholtzRotationTerm`: Helmholtz-splits the pair via `k_hat(k_hat.V)` in Fourier space into solenoidal + irrotational, rotates only the solenoidal part by a learned per-sample phase, leaves irrotational untouched by this term.
- `ArbitraryComplexPhaseTerm`: control -- same mechanism, same param budget, rotates the whole `V(k)` with no Helmholtz split. Isolates "does an undifferentiated Fourier phase rotation help at all" from "does targeting the physically-correct part matter."

**Real bug found and fixed via the mechanism test, not just asserted**: a uniform per-sample phase applied to every `rfft2` bin corrupts the round-trip at the `kx=0` and (`w` even) `kx=w/2` columns -- confirmed empirically (not just derived): rotate-then-`irfft2`-then-`rfft2` mismatches the original at literally every `ky` in those two columns and nowhere else. Root cause: those are the only columns `rfft2`'s reduced last axis stores a conjugate-linked pair within (a genuine real signal forces `X[h-ky,0]=conj(X[ky,0])`); a single global phase (not a matched `+-theta` pair across `ky<->h-ky`) breaks that whenever `theta != 0, pi`. `irfft2` doesn't raise or NaN on the corrupted input -- it silently returns *some* real tensor regardless of what it's given, so the corruption only showed up when the mechanism test re-extracted the spectrum and found the solenoidal magnitude had drifted ~267% instead of being exactly preserved. Fixed with `_rfft_rotatable_mask` (excludes those two columns from rotation entirely, phase=1 there, left alone) -- costs ~2/Wf columns' worth of bins never rotating, in exchange for an exactly-consistent round-trip everywhere else, confirmed to 8e-7 relative precision for both terms after the fix.

If they don't, the Helmholtz split isn't separating "vortical" from "compressive" structure at all, it's applying an arbitrary orthogonal change of basis (real ↔ Fourier, then a k_hat-based sub-split) to content that has no such structure, and then *restricting* the rotation to only half of an arbitrary split -- less freedom than the control's unrestricted rotation of the whole pair, for a physical distinction that may not correspond to anything in what those channels actually carry. The control's unstructured rotation had no such potentially-wrong constraint. Untested: whether designating a vector-pair from a location actually likely to carry velocity-like structure (e.g. probing which latent channels correlate most with decoded velocity, or channels feeding `use_streamfunction`'s stream_head) would change this -- this run picked channels [0:2] by convention, not by evidence they carry vector structure.

## 10. Two follow-ups from the Helmholtz-rotation result: residual decode, and pixelwise phase conditioning

Two new, independent ideas, tested in parallel (quick2/7-epoch, same protocol, one per GPU): a decoder-level residual/skip architecture, and fixing the exact expressiveness gap §9's "working hypothesis" flagged.

**`AnchorFusionHead` (residual decode)**: `decoders/anchor_fusion.py`, wired into `LatentDynamicsModel` via a new optional `anchor_fusion` constructor arg (`None` default, unchanged behavior for every existing config). Each of the K rollout predictions is concatenated channel-wise with a *fixed* anchor -- `x_context[:, -1]`, the last real context frame, reused at every step, not chained to the model's own previous prediction (deliberately, to avoid compounding a bad early prediction through the fusion mechanism itself) -- and a small conv net produces a correction added on top: `response_t = raw_t + correction(concat[raw_t, anchor])`. Correction net's last layer is zero-inited (this codebase's standard convention), so it's an exact no-op at init. Applied only to the rollout predictions, deliberately *not* to `anchor_target`'s own initial-frame reconstruction decode -- fusing that decode against the same frame it's scored against would let the network trivially ace that loss component by copying the anchor, undermining what `anchor_target` is there to check. Confirmed via mechanism test: exact no-op at init, real dependence on both `raw` and `anchor` once trained, gradients flow to both, and the full `LatentDynamicsModel`-level wiring (including the anchor_target-bypass) verified end to end before touching real data.

## 11. Does the pixelwise win scale with more pairs? And a first perceptual-loss attempt.

Two follow-ups, again one per GPU, quick2/7-epoch, same protocol throughout.

**Generalized `HelmholtzRotationTerm` to `n_pairs` independent vector pairs.** `vector_channels` may now span `2*n_pairs` channels instead of exactly 2; each pair gets its own Helmholtz split and rotation, no mixing across pairs. The phase-predicting module (`phase_net`/`phase_head`) is **weight-shared** across pairs, not duplicated -- pairs are folded into the batch dimension (`[B,n_pairs,2,H,W] -> [B*n_pairs,2,H,W]`, unfolded after), so `torch.fft` batches over pairs for free and parameter count stays exactly what it is at `n_pairs=1` regardless of how many pairs are used (confirmed: 12,321/142,324 params identical at `n_pairs` in `{1,2,4,8}`). New presets `film_helmholtz_rotation_pixelwise_{x2,x4,x8}`. Confirmed via mechanism test: `n_pairs=1` exactly matches the pre-generalization behavior, pairs are fully independent (perturbing one pair's content only changes that pair's own output delta), and every pair still exactly preserves its own solenoidal magnitude independently.

**Real measured cost, not estimated** (steady-state time/batch, same GPU): baseline ~420ms, `n_pairs=1` ~445ms (+6%), `n_pairs=2` ~478ms (+14%), `n_pairs=4` ~548ms (+30%), `n_pairs=8` ~657ms (+56%) -- close to linear in `n_pairs`, ~25-30ms/pair marginal cost, no blow-up.

**Result: `n_pairs=4` lands worse than both baseline and `n_pairs=1` at every epoch, finishing 0.2495 vs baseline's 0.2389 (4.4% worse) and `n_pairs=1`'s 0.2292 (8.9% worse).** `n_pairs=1` is not a floor to keep climbing past by covering more channels -- confirms the reading that only one pair had any real reason to carry vector-like structure; extending the same treatment to 3 more arbitrary pairs costs more than it buys.

**New: `spectral_loss`** (`training/losses.py`), a genuinely new (loss-level, not architectural) mechanism -- log-space L1 between predicted and target power spectra (`|rfft2(field)|^2` per bin, all 4 channels, `norm="ortho"`), built on the same idea `physics_diagnostics.py`'s `spec_*_hf_frac` already measures as a read-only diagnostic but turned into something actually optimized against. Added to `well_style_vrmse`'s rollout loss via a new `--spectral-weight` CLI flag (default 0.0 = off, plumbed through `train.py`). Confirmed via mechanism test: zero at exact match, grows with prediction error, gradients flow -- and specifically, a blurred field scores markedly worse (5.85) than comparable-MSE unstructured noise (1.24) against the same target, confirming it targets blur specifically, not error in general. `valid_loss` reporting is unchanged (still pure `well_style_vrmse`, confirmed by reading the val loop) so results stay comparable to every other number in this file.

**Result at weight=0.1: also behind baseline** -- 0.2590 vs 0.2389 (8.4% worse), and non-monotonic at the end (ticked up from ep6's 0.2562). **Important caveat this comparison doesn't resolve**: `spectral_weight` deliberately trades some vRMSE for sharper spectra -- that's its entire purpose, confirmed by the mechanism test's blur-vs-noise result. A worse `valid_loss` here doesn't mean the mechanism failed at its actual goal (visually less blurry output); it means that tradeoff hasn't been checked directly yet. Worth an actual visual/qualitative comparison of decoded rollouts (not just the vRMSE number) before judging this one either way -- untried.

**Open threads from this round**: whether a *different* (non-arbitrary) choice of pair -- e.g. probing which latent channels actually correlate with decoded velocity, flagged as untried back in §9 -- would make `n_pairs>1` pay off where an arbitrary extension didn't; a lower `spectral_weight` or more epochs for the spectral-loss run (it was still improving, just from a worse starting point, and hadn't clearly plateaued); and the qualitative check spectral_loss's own premise depends on.

## 12. Broad8 confirms `n_pairs=1`; giving `LatentDynamicsModel` a complex branch, three ways to conserve it, and a fusion-mode question

**Broad8/7-epoch confirmation of `n_pairs=1` (the session's best result)**: same config, full 8-combo protocol instead of quick2, single seed. Final valid_loss **0.2266** (best epoch 5: **0.2258**) -- beats the ~0.229 reference from the older (deleted) architecture family by ~1.1-1.4%, and confirms the quick2 win (4.1% over baseline) isn't a small-subset artifact. Epoch-by-epoch: 0.2922 / 0.2470 / 0.2571 / 0.2396 / 0.2258 / 0.2338 / 0.2266.

**Giving `LatentDynamicsModel` a complex branch it never had.** The existing `ComplexAmplitudeTerm`/`ComplexRotationTerm`/`spectral_grid` machinery only ever got wired up in `FoundationModel` (a different model class/dataset mix); `LatentDynamicsModel` had no way to initialize `z0.spectral_grid` at all, so `complex_term=True` there would crash. Factored `FoundationModel`'s own `complex_proj` construction out into `SpectralInitProj` (`encoders/field_embedder.py`, next to the `rfft2_crop` it already used) and added an optional `complex_proj` slot to `LatentDynamicsModel` (`None` default, zero effect on any existing config) plus `build_complex_proj`/a `complex_proj:` config block. Same zero-init rationale as the original: an unconstrained projection feeds an uncontrolled random-scale `spectral_grid` into the multiplicative `exp(amplitude+i*rotation)` update, which is exactly what caused the original complex-branch attempt to diverge (per this file's own earlier history). Confirmed via mechanism test: at init, the complex-branch model decodes **identically** to the plain real-only model with the same seed (zero-inited complex branch is a true no-op through `LatentState.grid`'s `irfft2` fusion).

**New preset `FiLMHelmholtzRotationComplexTransportOperator`**: the `n_pairs=1` real-branch winner, plus `complex_term=True`. `conserved_complex_channels` (default 0) reserves that many of the complex branch's 16 channels for some form of conservation; `conserved_complex_channels=0` is a plain, fully unconserved dual branch (the control).

**First attempt, `complex_conservation_mode="mask"`**: masks `amplitude` to exactly zero on the reserved channels, reusing the existing amplitude/rotation split (`exp(0+i*rotation)=exp(i*rotation)`, a pure phase multiply) -- no new math, just don't use half of what's already there. **The user immediately flagged the real problem with this**: it freezes every reserved channel's magnitude *independently at every single frequency bin* -- not one conservation constraint but thousands of separate rigid ones, far harsher than real energy conservation (which allows redistribution, e.g. turbulent cascades moving energy between scales) and a regression from `ConservedRotationTerm`'s own earlier (correct) design, which mixes *across* channels via an exact orthogonal `matrix_exp` rather than freezing each one.

**Two fixes, both genuinely allowing redistribution while conserving an aggregate**:
- `complex_conservation_mode="renormalize"`: let amplitude+rotation apply completely freely to the reserved channels (full redistribution across channels AND frequencies), then rescale the whole reserved block by one real scalar per sample so its TOTAL energy (summed over channels and every bin) matches its pre-step value. **Real bug caught and fixed**: `sqrt(e_before/e_after)`'s gradient blows up as its argument approaches zero -- and this mechanism starts at *exactly* zero (zero-inited `complex_proj` → `spectral_grid=0` at true init) -- which corrupted gradients badly enough to crash the SOAP optimizer's `eigh`-based preconditioner within the first few steps. Fixed by computing the scale in log-space with a hard clamp (`±2.0`, ~7.4x max correction/step) -- outside that range the gradient is exactly zero, cutting the feedback loop off entirely rather than damping it (deliberately not the smooth tanh-bounding this file usually prefers -- the goal here is protecting against a blow-up, not shaping a normal operating range).
- `complex_conservation_mode="unitary"`: new `ConservedComplexMixTerm` -- at *every individual frequency bin*, predicts an `n_conserved x n_conserved` skew-Hermitian generator, exponentiates it (`torch.linalg.matrix_exp`, confirmed to support batched complex/skew-Hermitian -> unitary matrices, ~1e-6 precision) into a genuine unitary transform, and mixes the reserved channels with it. Total magnitude across those channels is exactly conserved *at that bin*, redistribution allowed among channels there. The direct complex/per-bin generalization of `ConservedRotationTerm`'s own already-correct real-branch mixing. Replaces amplitude+rotation entirely for the reserved channels (owns their evolution completely, same pattern as `ConservedRotationTerm`).

Both confirmed via mechanism test: exact aggregate conservation, genuine per-channel redistribution (individual channel magnitudes free to move), zero-init no-op, gradients flow.

**Results (quick2/7-epoch, real branch always `n_pairs=1`, single seed each)**:

|---|---|---|
| Real-only `n_pairs=1` (reference) | **0.2292** | ~445ms |
| `unitary` | 0.2302 | ~565ms (+27%) |
| `renormalize` | 0.2317 | ~505ms (+13%) |
| Plain complex, unconserved (control) | 0.2324 | ~500ms (+12%) |

**Every complex-branch variant is strictly worse than real-only `n_pairs=1` on both cost and accuracy** -- none is cheaper or more accurate than simply not adding the complex branch at all. But the *shape* of the result validates the redistribution hypothesis cleanly: `mask` (harshest, no redistribution) is worst; `renormalize` and `unitary` (both genuine redistribution, different scopes) are close behind each other and closest to real-only; `unitary` (the most complete, structurally-faithful redistribution -- per-bin, not just a global rescale) came from behind (worst of the three through epoch 4, 0.2508) to finish best of the complex variants, only ~0.4% behind real-only. Net: `n_pairs=1` real-only remains the actual result worth keeping; the complex-branch direction is a settled negative result for this codebase/protocol, not a tuning problem -- but `mask` -> `renormalize`/`unitary`'s trajectory is real evidence the "balance, don't freeze" critique was correct in kind, just not enough to overcome the complex branch's fundamental cost/no-new-information problem (see below).

**Working theory for why the complex branch never pays off here**: it's bolted onto an already-well-optimized real branch. `n_pairs=1` Helmholtz rotation is itself the product of a real architecture search; advection/diffusion/skew/forcing/Helmholtz-rotation are already extracting most of the useful dynamical structure from the same information the complex branch would use. `SpectralInitProj` only ever looks at the raw input once, at t=0, then the complex branch evolves independently with much smaller, freshly-initialized nets, competing for the same fixed 7-epoch budget -- there may not be much genuinely new signal for it to find, and meanwhile it dilutes optimization rather than adding capacity that pays off in this budget.

**Fusion mode -- add vs. concat, in progress.** `LatentState.grid` (used everywhere, including `FoundationModel`, left completely unmodified) fuses via `real_grid + irfft2(spectral_grid)` -- a fixed additive combination decided before the decoder ever runs. New free function `fuse_latent(z, mode)` in `core/states.py` (`mode="add"` regression-tested bit-identical to `.grid`) adds `mode="concat"`: `torch.cat([real_grid, irfft2(spectral_grid)], dim=1)`, 2x channels when a complex branch is present, letting the decoder itself learn how (or whether) to combine the branches instead of having a fixed combination imposed on it. Wired via a new `LatentDynamicsModel.fuse_mode` constructor arg (`"add"` default, unchanged behavior; config: `model: {fuse_mode: concat}`) -- requires `decoder.latent_dim` set to `2x` the encoder's own `latent_dim` when a complex branch is attached, no decoder code changes needed (its `latent_dim` is just its first conv's input channel count). One expected, not-a-bug property: unlike every other mechanism in this whole thread, concat mode *can't* start identical to the real-only model at init -- it needs a wider, freshly-initialized decoder, so the zero-init-no-op property that held everywhere else doesn't apply here. Direct single-variable comparison config against the plain-complex control (`context_cond_helmholtz_rotation_complex_concat.yaml` vs `..._complex_control.yaml`, same real+complex setup, only the fusion differs).

## 14. Multi-horizon evaluation: the winner is unstable well past its training horizon

Every number in §9-13 was measured at roll6 -- the model was never once evaluated (or trained) at a horizon different from what it was trained on. Reloaded the existing quick2-trained checkpoints (baseline `context_cond_helmholtz.yaml` ep7 0.2389, winner `context_cond_helmholtz_rotation.yaml` ep7 0.2292 -- no retraining needed, rollout length is a runtime parameter) and rolled both out to 32 steps (RB trajectories are 200 steps long, plenty of room), computing `well_style_vrmse` per step instead of averaged over the rollout.

**Result**: the winner's advantage peaks almost exactly at the training horizon (step 7: +6.1%), decays smoothly through step 17 (+1.3%), then **crosses over and diverges catastrophically** -- step 18: -1.9%, step 24: -108%, step 32: -1225% (winner error 57.55 vs baseline's 4.34, a ~13x gap). The shape is a sharp regime change, not gradual chaotic drift (which would show smooth exponential growth throughout) -- consistent with an actual numerical instability being crossed, not just normal chaotic-system error growth.

**Revised conclusion**: `n_pairs=1` is not a universally better mechanism -- it's better specifically near the horizon it was trained/evaluated at (every comparison in this entire session used roll6), and unstable well past it. Working theory: `HelmholtzRotationTerm`'s rotation is exactly norm-preserving in isolation, but sums additively with advection/diffusion/forcing every step, unmasked -- nothing in training discouraged the phase net from learning something that compounds badly over dozens of iterations, since training only ever optimized 6-step accuracy. Diffusion provides real damping that keeps baseline bounded at long horizons; the added rotation has no built-in dissipation of its own.

**Not yet done**: retraining at a longer rollout horizon (plausible fix -- the model would then be optimized against the actual failure mode instead of extrapolating blind), and the same multi-horizon check on the plain-baseline-vs-`n_pairs=1` broad8 pair (no broad8 baseline checkpoint exists to compare against, per §12's known gap) and on the removed mechanisms generally (whether `mask`/mask-family conservation is actually *more* long-horizon-stable than the winner, given it's a harsher/more constrained mechanism, is an open question the consolidation closed off testing).

## 15. Gradient checkpointing: training at long rollout horizons at the same batch size

§14's finding raised the obvious follow-up: does training directly at a longer rollout horizon fix the winner's long-horizon instability, rather than just extrapolating a roll6-trained model past what it ever saw? Training at `rollout_steps=16` at the usual `batch=8` OOM'd -- long sequential rollouts keep every step's activations resident for backward, and decoding all `B*T` frames in one batched call compounds it. Dropping to `batch=4` "fixed" the OOM but introduces a real confound (different gradient noise) against every other number in this file, all at `batch=8`.

Added `LatentDynamicsModel.use_checkpointing` (`False` default, zero effect on any existing config) instead: gradient-checkpoints each rollout step (`rollout_latent`/`_checkpointed_step`) and the decoder call, trading ~20-30% more compute for memory that no longer scales with rollout length. Two things worth being precise about, since checkpointing is a solved technique but easy to half-implement:
- Confirmed via direct comparison (identical seed, with/without checkpointing) that forward output and gradients are **numerically identical** (0.00e+00 and 2.24e-08 respectively, the latter just chunk-order float noise) -- checkpointing recomputes the exact same forward pass, it's not an approximation.
- Checkpointing the operator rollout alone wasn't sufient -- the decoder's single call over all `B*T` flattened frames was the *other* dominant cost, and checkpointing *that* as one single call didn't help either: checkpointing only changes *when* activations exist (freed after forward, recomputed during backward), not their *peak* size for whatever's inside one checkpointed call. Chunking the decoder's checkpointed calls (one rollout-step's worth of frames per chunk, not all `B*T` at once) is what actually bounds the peak.

Result: `roll16` at `batch=8` (matching every other run in this file) now trains cleanly, confirmed with a real dry run -- ~1343ms/batch vs uncheckpointed `roll6`'s ~445ms/batch (real cost: longer rollout + recompute overhead, not just the checkpointing tax alone). Config: `model: {use_checkpointing: true}`.

## 16. Curriculum over rollout length: another angle on the same failure mode

§14's divergence and a separate observation both point at the same root cause: training loss is reconstruction + uniform-mean-over-the-rollout `well_style_vrmse`, every step weighted equally regardless of how much the autoregressive state has already drifted from ground truth. Once step 1 is off, later steps become increasingly uncertain targets for a squared-error loss, which regresses toward the mean -- i.e. blurs. This plausibly explains *both* things noticed independently: quick2 t+1 accuracy trailing published single-step benchmarks even though roll6-averaged numbers were strong, and §14's long-horizon divergence (a model that's never had to recover from its own drift at long horizons has no training signal telling it not to compound instability).

Two candidate fixes: (1) reweight the existing fixed-length rollout loss to downweight later/uncertain steps, (2) curriculum over rollout length -- train on short rollouts early, ramp the training-time horizon up over epochs, so the model spends early training nailing short-horizon accuracy (fixing the t+1 gap directly) before ever being asked to hold up over long autoregressive chains. Chose (2).

**Implementation** (`train.py`): `_curriculum_k(epoch, total_epochs, k_start, k_end)` -- linear ramp, one step per epoch, `round()`+clamp to `[1, k_end]`. New `rollout_curriculum_start: int | None` param (`None` default -- unchanged behavior, fixed `rollout_steps` every epoch). When set, each epoch computes `k_train = _curriculum_k(...)`, trains on `xb -> yb[:, :k_train]` at `steps=k_train` instead of the fixed target `K`, and `initial_weight = 1/k_train` scales with it. **Validation is deliberately left unchanged** -- always evaluates at the full target `K` -- so `valid_loss` stays comparable epoch-to-epoch and against non-curriculum runs; only the training-time rollout horizon curriculum-ramps, not what's being measured. New CLI arg `--rollout-curriculum-start`.

**Validated with a real-data dry run**, not just unit-tested math: `--rollout-curriculum-start 2 --rollout-steps 8 --epochs 3 --batch 2 --steps-per-epoch 5`, reference winner config (`context_cond_helmholtz_rotation.yaml`), real `rayleigh_benard` dataloader. `k_train` ramped exactly as designed (2 -> 5 -> 8 over 3 epochs), no shape-mismatch errors anywhere pred/target shapes flow through (loss, `compute_physics_diagnostics`, periodic `sample_vrmse` logging all needed fixing to use the sliced `yb_k` instead of full `yb` -- done), checkpoints saved cleanly every epoch, exit code 0. `valid_loss` (fixed roll8 throughout): 1.26 -> 1.39 -> 1.18 -- too few steps/epoch (5) to read as signal, just confirms the harness runs end to end.

**Not yet done**: a real launch (meaningful `steps_per_epoch`, full `quick2`/`broad8` protocol) comparing curriculum vs. fixed-horizon training, and re-running the §14 multi-horizon NRMSE eval against a curriculum-trained checkpoint to see whether it actually closes the long-horizon gap and/or the t+1 shortfall.

## 17. §14's divergence was a pure extrapolation artifact -- training at roll16 fixes it

§15 built the checkpointing needed to train `roll16` at `batch=8`; both `context_cond_helmholtz_roll16.yaml` (baseline) and `context_cond_helmholtz_rotation_roll16.yaml` (winner) finished quick2/7-epoch. Final `valid_loss` (well_style_vrmse, fixed roll16 the whole time): **baseline 0.3772, winner 0.3574** -- winner still ahead by ~5.2%, in line with its roll6 margin (0.2389 vs 0.2292, ~4.2%). Directly training at the longer horizon didn't cost the winner its edge.

Reran §14's fixed-reference NRMSE multi-horizon eval (`eval_horizon_nrmse.py`, same protocol, batch=2/40-batch cap) against these roll16 checkpoints instead of the roll6 ones -- same real question, now with a model that's actually seen its own 16-step compounding error during training, not just extrapolated past roll6 blind:

|---|---|---|---|
| 1 | 0.1927 | 0.1862 | +3.4% |
| 4 | 0.2614 | 0.2473 | +5.4% |

**No catastrophic blowup.** §14's roll6-trained extrapolation showed a sharp regime change at step ~18 -- winner advantage crossing from +1.3% to -1.9% to -1225% (57.55 vs 4.34 absolute error) by step 32, a real numerical instability being crossed. ## 18. §17's fix was a delay, not a cure -- roll16-trained winner still blows up past ~step 70-90

Built two inspection tools (`src/niko/eval/inspect_checkpoints.py`, a static shareable HTML report, and `src/niko/eval/inspect_server.py`, a live local server that runs a fresh rollout on demand for any param combo/trajectory/start-frame in the validation set -- see their docstrings) to eyeball rollouts instead of only reading aggregate metrics. Using the live server to push rollout length far past anything tested so far (180 steps, vs. §17's 32) surfaced a real regression in the §17 conclusion.

**§17 said**: training directly at roll16 eliminates the catastrophic divergence found in §14 -- smooth curves through step 32, winner still ahead. **That's true only within the window §17 actually checked.** Pushing the same roll16-trained checkpoints (`winner_roll16`/`baseline_roll16`, quick2/ep7) to 180 steps (traj 0, Rayleigh=1e8/Prandtl=1, start frame 0) shows the winner's NRMSE tracking baseline closely through ~step 65, then visibly bending upward starting ~step 71, then going **unbounded**: step 80 winner=1.73 vs baseline=0.887 (2x), step 90 winner=29.1 vs baseline=0.843 (34x), step 100 winner=1009 vs baseline=0.856 (1179x), step 180 winner=1.15e16 vs baseline=1.34e11. Reproduced on a second trajectory (traj 2, same params): same qualitative shape, onset even earlier (~step 55-60 instead of ~70).

**Baseline does NOT blow up** -- it saturates around NRMSE~0.85-1.1 from roughly step 75 onward and stays there for the full 180 steps. That's the expected signature of a chaotic system's forecast decorrelating from the true trajectory (bounded, "might as well be predicting the climatological mean" territory) -- not an instability. The winner's growth past its onset point is qualitatively different: monotonic, accelerating, several orders of magnitude, no sign of saturating.

**Visual confirmation makes the mechanism obvious, not just the numbers**: pulled actual decoded frames (buoyancy channel) at steps 70/80/90/100 from the same rollout.
- Step 70: winner still shows plausible (if blurrier-than-GT) convection structure -- plumes visible, nothing alarming yet.
- Step 80: small, sharply-bounded circular blob artifacts start appearing, breaking the smooth field -- localized, not global blur.
- Step 90: the blobs are large, saturated, alternating red/blue -- clearly a growing mode, not chaotic drift. Baseline at the same step is just soft/blurry (graceful decorrelation), no blobs.
- Step 100: fully dissolved into fine-grained red/blue speckle -- a checkerboard-like high-spatial-frequency pattern, the textbook look of an unstable mode concentrated near the grid's highest resolvable wavenumber (Nyquist).

**Revised understanding**: §14's original working theory holds, but §17 undersold it. `HelmholtzRotationTerm` rotates the solenoidal part of a 2-channel vector pair via a learned per-frequency-bin phase every step, summed additively with advection/diffusion/forcing, with nothing in its construction bounding the composed step map's spectral radius below 1 -- diffusion damps high-k content in the rest of the operator, but the rotation branch has no such damping of its own, and training only ever supervises finitely far (6, then 16 steps). Training at roll16 (§15/§17) didn't remove the unstable mode; it just meant the mode's growth hadn't yet become visible by step 32, the furthest §17 checked. The instability is still there, still exponential, just pushed further out -- consistent with training-horizon exposure delaying onset roughly in proportion to how far training looked, not curing an eigenvalue problem. A curriculum run trained further out would likely push the onset out further still, but by the same logic would still have *some* onset unless the mechanism itself gets bounded (e.g. clamping/damping the phase net's effective rotation magnitude, or an explicit dissipative term on the rotation branch) rather than just training longer.

**Not yet done**: confirming the exact onset step scales with training horizon (would need the still-in-progress curriculum/roll16 checkpoint, or a longer-horizon training run, to compare); checking whether it's specifically high-k bins blowing up (the checkerboard pattern strongly suggests it, but no direct per-bin spectral trace was taken); any fix attempt (damping/clamping the rotation phase net, or an explicit dissipation term on the rotated branch).

**Follow-up: does rollout-curriculum training (§16) delay/fix the blowup? No -- it makes it dramatically worse.** Trained the winner (`context_cond_helmholtz_rotation_roll16.yaml`) with `--rollout-curriculum-start 2`, quick2/7-epoch, same protocol as the fixed-horizon `winner_roll16` checkpoint otherwise. Roll16 valid_loss came in slightly *worse* than fixed-horizon training too (curriculum 0.3745 vs fixed 0.3574, ~4.8% worse) -- curriculum bought nothing on the metric it was actually designed to help, in this specific case. Then re-ran the same 180-step single-trajectory extrapolation (Rayleigh=1e8/Prandtl=1, traj 0) against both checkpoints:

|---|---|---|
| 31 | 0.284 | 0.292 |

Working theory: curriculum's early epochs spend real optimization budget at very short rollout (`k_train=2`), where the rotation mechanism's long-horizon instability is completely invisible to the loss -- if anything this looks like it lets the phase net drift further from whatever implicitly-stable region fixed-horizon training's constant 16-step exposure was keeping it near, before ever seeing a longer rollout to correct it. **This settles the "maybe curriculum fixes it" question for this mechanism: it doesn't, and makes a reasonable case it's actively counterproductive here.** Curriculum's original motivation (§16, the t+1/blur hypothesis) is untested by this -- this only speaks to long-horizon stability, and only for the winner's rotation mechanism specifically, not curriculum training in general or the baseline (no non-blowing-up mechanism to make worse).

## 20. DISCO-inspired sub-step integration tames the §18 blowup, at inference time, with zero retraining

Read Morel et al.'s DISCO paper (arXiv:2504.19496) at the user's prompting. Setting aside its two headline architectural choices (a meta-learning hypernetwork, and no latent space at all -- it integrates directly in physical data space), one specific mechanism stood out as directly relevant to §18: DISCO never predicts `u_{t+1}` from `u_t` in one shot. It treats the update as a continuous-time ODE and integrates it with an adaptive Runge-Kutta scheme, up to 32 sub-steps per output frame, backpropagated via the adjoint method (constant memory, a different answer to the same memory problem §15's checkpointing solved). Our `TransportOperator` does the opposite: one hard Euler-style update per frame, no sub-stepping, no stability margin -- and a step that's too large relative to the fastest/most oscillatory term in a system is *the* textbook cause of exactly the kind of runaway §18 found (a rotation term is about as oscillatory as a term gets).

**Implementation.** Added `dt: float = 1.0` threaded through `TransportOperator.forward`, `LatentDynamicsModel.rollout_latent`/`forward`, and `OperatorBase.validate_input` (needed since `validate_call` forwards the same kwargs to both). `n_substeps: int = 1` on `LatentDynamicsModel.forward`/`rollout_latent` calls the operator `n_substeps` times per output frame at `dt=1/n_substeps` instead of once at `dt=1`; only the requested output frames are decoded/returned, same contract as before. Every default is exactly the prior behavior (`dt=1.0`, `n_substeps=1`), so this is zero-risk for every existing config/checkpoint.

The subtlety that matters: **not every term can just be linearly scaled by `dt`.** `advection`/`diffusion`/`forcing`/`skew` already look like genuine PDE rate terms (`a·∇z`, `ν·Δz`, ...) -- `dz/dt = f(z)`, standard Euler sub-stepping, scale the output by `dt` and it's a normal finer-grained discretization of the same dynamics. `HelmholtzRotationTerm` is structurally different: it returns a *full finite rotation's* delta (`v_rotated - v`), not a rate -- scaling that delta by `dt` after computing a full-magnitude rotation isn't a smaller rotation, it's a linear interpolation toward one, a different and non-convergent operation. The correct fix is scaling the rotation *angle* `theta` by `dt` before computing `exp(i*theta*dt)` -- i.e., treating the phase net's raw output as an angular *velocity*, so `n_substeps` calls at `dt=1/n_substeps` sweep approximately the same total angle as one `dt=1` call would (exactly equal in the small-angle/frozen-theta limit; in practice `theta` gets recomputed each substep from the evolving state, which is the whole point -- a genuinely different, hopefully better-conditioned discretization the network was never trained under). `HelmholtzRotationTerm.forward` and `complex_term`'s amplitude/rotation both got this angle-scaling treatment, not a post-hoc delta scale.

**Result: dramatic, on both trajectories tested, purely at inference time on the already-trained `winner_roll16` checkpoint -- no retraining.** Same 180-step extrapolation as §18 (Rayleigh=1e8/Prandtl=1), NRMSE (fixed ref), swept `n_substeps` in {1, 2, 4, 8, 16}:

**GPU-memory rescale.** A blanket 2x-every-width pass (predating this write-up) blew a `core3`-tuned model's footprint out to 114GB/183GB on a B200 for a model with only ~2.3M params. Traced actual memory flow per-dimension instead of scaling uniformly: `latent_dim` (real+complex spectral grid held live across the whole rollout for backprop) and `decoder_hidden_dim` (conv over the rollout flattened into the batch dim) are the two real levers; `hidden_dim` is real but downsampled; `canonical_dim` is full-resolution but only 1x1 convs (linear, no rollout multiplier); `cond_dim` feeds only a small pooled Linear/FiLM MLP, essentially free. Reverted `latent_dim`/`hidden_dim`/`decoder_hidden_dim` to `core3`'s original values, kept `canonical_dim` modestly up (16 vs 12), pushed `cond_dim` up (32, later corrected -- see below). GPU footprint dropped to 55GB.

**Training-volume was the dominant, and largely settled, explanation for underperforming historical single/few-task baselines.** `train_foundation.py` inherited a fixed `--steps-per-epoch 800` from `all14`'s need to balance 14 wildly-different-sized datasets -- but applying that same fixed budget to 1-3 task runs meant "5 epochs" was only 4,000 total steps, vs. the historical `broad8`/`shear_flow_broad8` protocol's natural-length epochs (**13-20x more total training**: `rayleigh_benard`'s natural epoch alone is 7,560 batches). Confirmed conclusively: single-task `rayleigh_benard`/`broad8` at natural-length epochs, 7 epochs, reached valid_loss **0.254** (historical best: 0.229, range 0.211-0.280); the identical 2-task `rayleigh_benard`+`shear_flow` config reached **0.289** / **0.379** respectively (shear_flow's historical best: 0.385) -- both land right in or beat the historical range. A `PooledContextCondEncoder`-vs-`ContextCondEncoder` architecture fix (matching the actual winning `configs/context_cond_pooled_helmholtz.yaml` recipe -- see §7 above) and a `cond_dim` revert (128→32, the value that config actually uses) were tested and found real but NOT the dominant factor (near-identical numbers with or without, epoch-for-epoch) -- kept anyway since they match the known-good recipe, but training volume is what actually closed the gap.

**Boundary-condition blindness, found and fixed.** Pulled every task's actual HDF5 `boundary_conditions` group: **at least 6 distinct per-axis BC regimes** across the 12 tasks (periodic / wall-Dirichlet / wall-no-slip / open / open-Neumann / mixed-asymmetric) -- only 3 of 12 tasks fully periodic. The operator's spatial derivatives (`dx_central`/`dy_central`/`laplacian` in `transport_terms.py`) and the streamfunction-derived velocity decode (`core/states.py`) were both hard-coded to `torch.roll` -- unconditionally periodic, for every task, always, on every rollout step. Built `core/boundary.py`'s `blended_pad`: a per-sample learned soft blend of zero/circular/replicate padding (softmax over 3 weights per axis), replacing every hard-coded `torch.roll` call, driven by a new `BoundaryGeometryHead` off pooled context, zero-inited to start at exactly the old 100%-circular behavior (verified bit-identical to the pre-fix code at init). **First version was a real bug**: one `BoundaryGeometryHead` shared across all 12 tasks, which -- inspected directly from checkpoint weights, not assumed -- converged toward whatever blend helped the aggregate 12-task gradient (mostly "replicate", including for `shear_flow`, which is genuinely fully periodic) rather than each task's actual geometry; `euler_multi_quadrants_openBC` (the one fully-open task) stayed essentially unmoved at ~99.9% circular the whole time. Fixed to one independent head per task (`nn.ModuleDict`), same failure mode and same fix shape as the field-embedder issue below.

**Field-embedder cross-task sharing, found and fixed.** 16 canonical field names across the 12 tasks, 11 of 16 used by exactly one task, but `FieldEmbedder` summed every task's raw channels through one *shared* embedder per field name regardless -- e.g. `velocity` funneled `rayleigh_benard`'s incompressible streamfunction-derived flow, `acoustic_scattering`'s linearized particle velocity, and `turbulent_radiative_layer_2D`'s compressible NS velocity through the identical embedder, despite the decoder side already treating these as physically different. Fixed to per-`(task, field)` embedder copies, warm-started identically (deep-copied from one shared prior per field, not independently random-initialized) then independently learnable.

**Checkpoint-format drift, fixed structurally, not patched.** Root cause of `BoundaryGeometryHead`'s weights silently never being saved (once it existed): the checkpoint format hand-enumerated every submodule into separate dict keys, and nobody updated that list when the new submodule was added. Replaced with `build_foundation_model(model_config: dict, device)` -- the single place a `FoundationModel` gets constructed, driven by a config dict, used identically at training start and checkpoint load -- and a save format that's just `{"model_state_dict": model.state_dict(), "model_config": model_config, ...}`. `model.state_dict()` walks the whole registered module tree automatically, so any future submodule is included with zero changes at the save site -- this is what actually closes the drift risk, not the one-off fix. Verified via bit-exact (`torch.equal`) round-trip after perturbing every parameter including the new submodule specifically.

**A real, verified `traj_limit` sampling bug.** `traj_limit`-based tasks (`euler_multi_quadrants_openBC`, `acoustic_scattering_*`, `gray_scott`, `viscoelastic_instability`) always trained/validated on the same fixed first-N trajectory indices (`n_traj = min(n_traj, traj_limit)`, a positional head-slice used as a literal HDF5 index) out of however many actually exist -- for `euler_multi_quadrants_openBC`, 3 of 400 per file, every run, forever. Verified as a real (not just theoretical) bias: initial-condition severity varies ~8-10x across trajectory index in one checked file, and the always-picked indices 0-2 happened to be mild, meaning genuinely extreme realizations (e.g. index 20, 155) were never seen by train OR validation, ever. Fixed to a seeded random sample (`traj_seed`, reproducible, varies per-file) instead of a positional slice.

**Spatially-adaptive `DiffusionTerm`.** Was one scalar `nu` per sample (`exp(Linear(cond_dim,1)(cond))`), spatially uniform and state-independent. Rewritten to read `z.real_grid` (not just `cond`) through the same `_conditioned_net` conv-net pattern `AdvectionTerm`/`ForcingTerm` already use -- `nu` is now a genuine nonlinear function of the current field state, closer to a real diffusivity closure (eddy diffusivity / boundary-layer effects / heterogeneous media all vary spatially and with local state in reality). Zero-inited output conv reproduces the old scalar version exactly at init (verified to ~1e-9, float32 rounding only). **Notably, this is the same idea §22 above arrived at independently and concurrently** via a differently-shaped `LocalDiffusionTerm` (local `nu_head(cond) + local_net(z, cond)` correction on top of a kept-scalar floor, vs. this session's full replacement) -- both survived the later local/AICR consolidation as separate selectable terms (`diffusion` now IS the adaptive version; `local_diffusion` is still available too), genuinely redundant in spirit but cheap to leave both available for ablation.

**A 24-then-28-job operator-term ablation matrix**, per explicit request for something "somewhat robust" across more than one task: `baseline` (all 4 default terms + complex-term) / leave-one-out for each of `advection`/`diffusion`/`skew`/`forcing` / `no_complex` / `adaptive_diffusion`, x `rayleigh_benard`, `active_matter`, `gray_scott_reaction_diffusion`, `acoustic_scattering_discontinuous` (chosen specifically as the two cheapest `all14` tasks by real resolution×channel cost, not just batch count -- `euler`/`helmholtz_staircase` are deceptively expensive by that measure and were deliberately excluded). 10 epochs, natural-length, ctx6/roll6 throughout.

**Results, `active_matter` (complete): every term helps, consistent direction.** `baseline` **0.386** (best) < `no_diffusion` 0.403 < `no_skew` 0.417 < `no_advection` 0.434 < `no_forcing` 0.467 < `no_complex` 0.498 (worst) -- complex-term matters most, diffusion least, nothing actively hurts.

**Results, `rayleigh_benard`: an early, opposite-direction signal that was never resolved to a confident conclusion.** Through ~4-5 of 10 epochs, `no_diffusion` (0.261) and `no_skew` (0.260) were both tracking *better* than `baseline` (0.279) -- the reverse of `active_matter`. **This raised a real methodological concern, never fully closed**: separately-supplied PCGrad on/off comparison numbers for `rayleigh_benard`/`shear_flow`/`active_matter` showed non-monotonic noise at *different* epochs between the two conditions, which is diagnostic of plain run-to-run noise rather than a real effect -- meaning some fraction of these single-seed ablation gaps (this section's 0.005-0.02-scale differences included) may not be real. Proposed next steps, not yet executed: multi-seed repeats to establish a noise floor (a "fast4" -- `rayleigh_benard`+`active_matter`+`gray_scott`+`acoustic_scattering` -- 2-3-seed baseline sweep), instrumenting latent-state drift/per-term gradient norms directly instead of inferring stability from final loss alone, and a small LR bracket. **Given this uncertainty, don't treat this matrix's per-term rankings as settled** the way §21/§22's single-model comparisons are -- treat them as a first pass that surfaced a real open question about noise vs. signal, not a completed ablation study.

**12-task `euler_multi_quadrants_openBC` instability: reduced roughly 50x by the BC/field-embedder/traj_limit fixes above, but not solved.** Peak validation blowup went from 18,827 (pre-fix, shared BC head) to 375.98 (post-fix, per-task BC head, still-incomplete final epoch) -- a real, large improvement, but still a genuine outlier next to every other task's stable 0.1-0.8 range at the same checkpoint. Training-side loss for this task shows zero soft-cap trips across every logged epoch (the model trains stably), meaning the blowup is purely a validation-time phenomenon -- and validation loss has no cap/robust-statistic protection at all, unlike training's `soft_cap_loss`. This is the leading unfixed hypothesis (flagged repeatedly, never implemented): one genuinely extreme validation batch (`euler`'s data is confirmed the most heterogeneous initial-condition severity in the whole set) can still produce a wildly non-representative single number even with correct BC treatment underneath it.

**12-task vs. 3-task, and a training-volume confound that was never cleanly isolated.** Comparing the 3 tasks shared between a 3-task and a 12-task run (same BC/field-embedder fixes, same epoch count): 12-task was meaningfully worse on all three (e.g. `rayleigh_benard` 0.250 vs 0.320) -- but per-task training volume differed ~7x between the two runs (12-task capped at 1,600 steps/epoch to fit the 24h partition wall-clock limit; 3-task got natural-length ~12,096 steps/epoch), so this gap is very likely mostly volume, not task-count interference, but was never isolated with a dedicated same-volume ablation.

**A resolved false alarm, worth remembering as a general lesson**: PCGrad+loss-cap were suspected as a cause of the 12-task instability, tested both on and off at 12-task/elevated-volume scale, and **both configurations diverged -- just on different tasks each time** (on: `shear_flow`/`rayleigh_benard`/`euler` blew up, `viscoelastic_instability` fine; off: the reverse). This proved PCGrad/cap were never the actual cause -- disabling the loss cap made the worst-case blowup larger, not smaller, consistent with `soft_cap_loss`'s own documented purpose (bounds one anomalous batch's influence on gradient *direction*, not the underlying instability). Net conclusion, now the working default: PCGrad+cap are neutral at small task counts and actively protective at large ones -- keep them on.

**Operational lesson, recorded because it cost real GPU time once**: when polling a shared checkpoint save-directory for "did run X produce output Y", check the file's mtime against the run's actual start time (or grep the run's own log for the save line) -- never a bare filename-existence glob. A stale checkpoint left over from an unrelated earlier run in the same save-dir caused a false-positive "epoch complete" signal that led to cancelling an in-progress run at 87.5% through its final epoch.
